## Brand

- Personality: a quiet, capable and discreet companion for focused work. Warm without pretending to be human; direct without sounding mechanical.
- Trust signals: visible data destination, explicit memory scope, inspectable activity, honest uncertainty, reversible choices and precise confirmation before side effects.
- Avoid: mascot-led personality, performative intimacy, emotional dependency, surveillance language, hidden background work, opaque confidence scores and admin-console density in everyday flows. The reference-approved blue/purple gradient is limited to the Nexa brand mark.

## Product goals

- Goals: help users resume work quickly, retain useful context with consent, convert conversations into progress, suggest timely next steps and act only within explicit authority.
- Non-goals: therapy or crisis care, covert monitoring, autonomous destructive actions, screen control, automatic memory extraction, cross-device memory sync and a broad connector marketplace in companion v1.
- Success signals: first useful outcome within three minutes; a returning user can resume an active goal in one click; every stored memory is inspectable/editable/deletable; no unconfirmed memory writes; no side effect without a valid approval; proactive suggestions can always be dismissed, snoozed or disabled.

## Personas and jobs

- Primary personas: Vietnamese knowledge workers who use documents, Jira and Confluence and want continuity across focused work sessions.
- Secondary personas: security, IT and operations staff who need clear policy, diagnostics and data-boundary evidence.
- User jobs: capture context, understand information, continue an unfinished outcome, prepare or perform a bounded action, remember stable preferences and recover safely when a tool result is uncertain.
- Key contexts of use: focused desktop work, short return visits between meetings, document review, project follow-up and incident/error recovery.

## Information architecture

- Primary navigation target: Today, Conversations, Goals, Memory, Activity, Business Analyst workbench and Settings. Ship incrementally; do not expose an empty destination before its core flow works.
- Core routes/screens: Home/Today resume surface; conversation workspace; goal/commitment detail; memory ledger; agent activity timeline; connections/models/data settings.
- Content hierarchy: current focus and next action first, supporting context second, technical model/tool details on demand, diagnostics last.
- Current implementation note: the app exposes Today, Chat and Settings. The Business Analyst workbench adds a `Nghiệp vụ` destination that is hidden unless the `baWorkbench` feature flag is on. Memory v1 lives inside Settings. Commitment Engine v1 adds Goals as a first-class destination. Proactive Check-in + Agent Activity add an opt-in suggestion loop and the first-class Activity destination; neither surface may imply that Nexa remains active after its process exits. OS notifications and a tray icon add no destination: they are a second opt-in that reaches the user while the window is hidden, and Today keeps saying plainly that reminders stop when Nexa is closed. The daily briefing adds no destination: it replaces the top of Today, and like check-ins it only assembles while the process is alive.

## Design principles

- Remember with permission: Nexa never silently persists a personal fact. Memory shows source, scope, sharing policy and last confirmation.
- Suggest with a reason: proactive cards say why they appear now and provide Do, Later and Do not ask again controls.
- Act within a boundary: read, suggest and act are distinct agency levels. Existing approval, payload binding and uncertain-result behavior remain invariant.
- Continuity over chatter: optimize for resuming goals and commitments, not conversation count or message volume.
- Legibility over magic: expose what Nexa knows, what it is doing, where data goes and what remains uncertain.
- Tradeoffs: accept small consent friction and bounded context use in exchange for privacy, correction and long-term trust.

## Visual language

- Color: the user-approved light palette is the app default: canvas `#f5f9fe`, white surfaces, navy text `#141747`, blue actions `#1761ff`, selected navigation `#dfebfd`, and user messages `#e5efff`. Retain semantic success/warning/danger colors with contrast suitable for white surfaces. There is currently no theme switch.
- Typography: use a Windows-native, highly legible hierarchy initially (`Segoe UI Variable` with safe fallbacks); avoid a new font dependency until brand assets are approved.
- Typography sizing: after user feedback that the reference-derived type was too large, use 14 px navigation/model controls, 15 px chat/composer text, 12 px metadata, 20 px conversation titles and 28 px branding. Keep chat line-height at 1.55 for Vietnamese readability. Compact the sidebar to 272 px and controls to 42 px high; keep the short-window scrolling treatment.
- Spacing/layout rhythm: 4 px base rhythm, compact desktop workbench, generous separation between context, action and audit information.
- Shape/radius/elevation: retain 8 px form-control radii; use 14 px navigation/action corners, 16 px message panels, and a 24 px composer with subtle elevation, matching the reference. Avoid cards nested inside cards.
- Motion: short state transitions that explain progress; respect reduced motion; no ambient or decorative motion.
- Imagery/iconography: local inline SVG through `UiIcon` and the reusable `NexaMark`; no remote font/icon dependency. Icon buttons keep accessible names, visible focus, and functional actions. The reference logo is reconstructed; native window controls remain managed by Electron/the OS.

## Components

- Existing components to reuse: Sidebar, ChatView, Settings tabs/panels, ConfirmationDialog, DestructiveActionDialog, UncertainBanner, Toasts and semantic form/button styles.
- New/changed components: MemoryPanel, TodayView and GoalPanel are implemented. ChatGptAccountPanel owns ChatGPT-managed sign-in and the Codex entitlement catalog inside the OpenAI settings tab. ChatView combines configured API models and entitled Codex models in one grouped picker while keeping their providers visibly distinct. ProactiveCheckInService, TodayCheckInCard and AgentActivityTimeline are the next implementation slice; WorkingMemoryStrip remains a later phase.
- ChatGPT account contract: Nexa delegates the browser OAuth ceremony, token persistence, refresh and entitled model discovery to the local Codex App Server. The renderer receives only account email, plan label, summarized Codex rate-limit windows and sanitized picker-visible model metadata; it never receives an OAuth URL, access token, refresh token or raw App Server payload. Signing out is explicit and affects the shared local Codex account session.
- Codex model catalog contract: after a successful account read, load all picker-visible pages through stable `model/list`, mark the server-recommended default and show reasoning efforts/input modalities. Expose the same sanitized entries in the Chat picker under a separate `ChatGPT Plus / Codex` group; never copy them into the API-key model registry.
- Codex conversation contract: selecting a Codex model persists `chatgpt` plus the model id on the Nexa conversation, then sends turns through Codex App Server instead of an OpenAI-compatible API client. Each turn uses an ephemeral read-only thread, injects a bounded copy of prior Nexa user/assistant text, streams agent-message deltas into the existing message bubble and supports interruption. Nexa declines unsupported server-initiated tool/approval requests; text chat cannot inspect or mutate the local workspace.
- Codex attachment contract: the first chat integration is text-only even when a catalog entry advertises image input. File and image attachment stay disabled for `chatgpt` selections until Nexa has a reviewed, explicit external-data consent and media transport contract.
- GoalPanel contract: commitments are records with a concise outcome, one next action, lifecycle status, optional due/check-in time, optional source conversation and a creator (`user` or `agent`). Nexa never promotes a memory fact or chat statement into a commitment without explicit confirmation; a proposal may originate in chat, but only a confirmed preview writes the record.
- Chat commitment capture contract: `agentCommitmentToolsEnabled` is off by default. When on, the agent gets two local tools — create and update — that run in main, stay available without Atlassian, sit outside tool presets, and pass through the same confirmation guard as any external write (preview, one-shot approval, payload hash). There is no delete tool and the agent cannot set `completed`. Relative Vietnamese deadlines are resolved in main against the machine clock; anything unresolvable is refused rather than guessed, and previews always show the absolute date.
- Commitment lifecycle: `active`, `blocked`, `paused` and `completed`. Completing is reversible; permanent deletion remains a separate destructive action with confirmation.
- Today ordering: overdue check-ins and due dates first, then active work by recency. Every surfaced commitment explains urgency through its status/date instead of an opaque score.
- Proactive check-in contract: global opt-in is off by default. While the app process is alive, due/check-in timestamps may create one idempotent suggestion per commitment. Do/Later/Dismiss/Do not remind again only mutate local suggestion state; Do opens the source conversation or Goals and never sends a message, edits a commitment or runs a tool.
- OS notification contract: notifications are a second opt-in (`checkInOsNotificationsEnabled`) that is off by default and requires the check-in opt-in as well; enabling reminders inside the app never implies permission for content to leave the Nexa window. Notification bodies name a count, not a commitment, unless the user separately turns on `notificationShowContent` — the OS notification centre renders on the lock screen, is read aloud by assistants and syncs across machines on some Windows configurations, which puts it outside anything Nexa can encrypt. Every pending suggestion collapses into one notification per change, an already-notified suggestion never fires again, and a focused visible window stays silent because Today already said it. Clicking a notification or the tray's Open item restores, shows and focuses the window, then navigates to Today. `ProactiveCheckInService` gains no knowledge of the Notification API: the notifier subscribes to the `onChanged` port the service already exposes.
- Tray/lifecycle contract: the tray exists for the life of the process and is destroyed in `before-quit`. Minimize-to-tray is a separate opt-in for the minimize gesture only — closing the last window on Windows/Linux still quits the app, because a close-to-tray would keep the process alive indefinitely holding decrypted credentials in RAM. Pausing reminders for an hour from the tray is in-memory and blocks notifications only; it never touches suggestion, commitment or stored settings state. A tray icon that cannot be built on the current platform is logged and skipped, never fatal.
- Activity timeline contract: user-visible events are append-only structured metadata for suggestion, memory mutation, commitment mutation, tool preview, confirmation, tool result and uncertain operation, each attributed to an actor (`user` or `agent`). Timeline rows contain enums, timestamps and identifiers only; no raw payload, memory content, commitment next action, target URL or secret is stored for the timeline.
- Commitment context contract: `commitmentContextEnabled` is on by default and injects active/blocked commitments as their own system block, separate from memory, with an independent count and token budget. The block is framed as reference data, never as instructions, is dropped before the current turn when the budget runs out, and is withheld entirely from external providers.
- BaWorkbenchView contract: the `Nghiệp vụ` destination is the ONLY surface for business-analysis features. It owns confirmed business knowledge, structured documents and the error-code page. No BA state leaks into Chat, Today or Goals. The destination is hidden when `features.baWorkbench` is off, and every `ba:*` IPC channel is refused in main regardless of what the renderer shows.
- BA knowledge contract: business knowledge is a separate store from memory facts, not a new memory kind. Each item carries a category, a lifecycle (`draft` → `confirmed` → `outdated`), a source, an optional replacement pointer, conflict links and a usage count. Only user confirmation moves an item to `confirmed`, and only `confirmed` items enter context or serve as review evidence. Superseding replaces rather than overwrites so the history of a business decision stays readable.
- BA knowledge sharing contract: business knowledge is always internal. There is deliberately NO per-item sharing policy — memory has one because it is personal preference, whereas business knowledge is organizational property. The whole block is withheld from external providers, filtered once in the repository and again immediately before model invocation.
- BA document contract: a document is a list of typed items (field, use case, rule, flow step, error code, actor); prose is generated from that list, never the other way round. Items the extraction step could not determine are marked `needs_review`, shown separately and excluded from every summary and review conclusion. Item ids are unique per document, not globally.
- BA template contract: the standard template set and the field-validation rulebook ship as read-only resources (`ba-templates.json`, `ba-rulebook.json`) that IT overrides at distribution, exactly like `policy.json`. There is no end-user template editor: a standard each machine can edit is not a standard. A template names ordered sections, each marked required or optional and typed by the item kinds it holds, so "is this document on-template" is a count, not a judgement. Documents record the template id AND version they were written against.
- BA projection contract: the document view exposes four read-only projections computed from the same model — Markdown by template, a Mermaid flow diagram, a flow-step/use-case traceability matrix, and a field-validation audit against the rulebook. All four report what was checked, never whether the document is "complete". Near-duplicate pairs are offered for the user to merge; pairs that differ only by a negation are shown as suspected contradictions with no merge option.
- BA extraction contract: extraction is a bounded main-process job with schema-validated output, not a chat turn. Output that fails the schema is rejected and re-requested at most twice, then reported as a failure; nothing is coerced or defaulted. Re-running on unchanged source reuses the stored result without calling a model.
- BA review contract: every finding is produced by a pure rule function over the document model and confirmed knowledge, never by a model. Rules live in a versioned registry; the same document and the same rule pack version yield the same findings in the same order. No finding exists without a rule id, level and remedy. A rule that cannot run for lack of a template, rulebook or confirmed knowledge is reported as **not checked**, never counted as passed. Items marked `needs_review` are excluded from the evidence and the excluded count is shown. The report states which rule pack, which version and how many rules ran; it never calls a document "complete", not even when every rule passes — the pack checks structure and agreement with confirmed knowledge, and knows nothing about a requirement nobody has thought of.
- BA review assist contract: a model is used at exactly one point in review, and it never rules. Given a finding the code already produced, it may propose replacement wording for one field; only that string is read back, so output that adds, removes or downgrades findings has no effect. Applying a suggestion is a separate per-finding user action that edits one field of one item, re-validates against the item schema and records one activity row of ids and enums. There is no bulk apply, and the report never refreshes itself after an edit.
- BA review log contract: review logs and the diagnostics bundle carry document id, review id, rule pack id and version, and counts only. Finding text, item names, rule statements and severities are never written to a log or an activity row.
- Bank document checklist contract: a checklist case pins one organization-owned template id and version, contains encrypted structured evidence extracted from a set of files and produces a deterministic report. The model may classify documents and extract fields, but it never returns checklist status. Every result names a rule, evidence and remediation; uncertainty or a rule that cannot run is `needs_review`, never silently passed or treated as a missing document.
- Bank document privacy contract: source files and raw extracted text are transient and never copied into SQLite. Only encrypted file names, normalized fields and report payloads plus safe hashes/enums/counts persist. Bank document extraction is LiteLLM-only; an external provider is rejected before invocation. Scanned PDFs remain explicitly unreadable until the separate vision/OCR consent contract is approved.
- Bank checklist UX contract: the `Hồ sơ` tab is part of `Nghiệp vụ` and is hidden/refused with the same `features.baWorkbench` gate. It shows case/template identity, received documents, a status summary and a checklist table. It says “đạt theo các luật đã chạy”, never “hồ sơ hợp lệ”, “đầy đủ” or “đã phê duyệt”.
- Attachment format contract: the file picker offers exactly the formats the extraction pipeline accepts — text, PDF, Word, Excel, PowerPoint (both the modern XML and the 97-2003 binary generations) and PNG/JPEG/WebP/GIF images. Office and image readers are written in-repo with explicit ceilings on every decompression path, because the bytes come from untrusted files. A spreadsheet keeps its sheet names and column alignment; a deck keeps its presentation slide order and speaker notes; a legacy `.doc` is read through its piece table so deleted fragments and hyperlink field instructions never reach the model.
- Image attachment contract: an image is a document kind, not a separate attachment type, so it inherits the same picker, the same per-request limit, the same path hashing and the same provider policy. Images are accepted in Chat only: the Business Analyst and bank-checklist flows consume extracted text, so they refuse an image in main rather than sending the model an empty document, and their picker does not offer image formats. This refusal is what keeps the workspace image path stopped until its consent contract is approved. Metadata (EXIF, XMP, comments) is stripped before the image is encoded; if stripping fails the image is not sent. Images are never persisted in any encoding — a base64 copy is still a copy. Sending an image additionally requires a model the user has explicitly marked as able to read images; this capability check is separate from the document permission check and defaults to refusing, and an image that does not fit the context window fails the turn rather than being silently dropped.
- Daily briefing contract: the Today briefing is assembled by a pure function over local commitments and assigned Jira issues, grouped into exactly four urgency buckets (`overdue`, `due_today`, `due_this_week`, `in_progress`) against the machine's local day boundary. A model never decides which items appear, which bucket they land in, or their order. Jira is read through a single `jira_search` call whose JQL is built in main — never supplied by the renderer or a model — and each source reports its own status, so a broken source reads as a named failure with a recovery action rather than as "nothing due today". The briefing states its own scope: it covers commitments and Jira, and says plainly that it does not yet include meetings, because no calendar connector has been approved. Nothing in the briefing writes: it creates no commitment, generates no check-in, and calls no write tool.
- Briefing summary contract: `dailyBriefingSummaryEnabled` is off by default and is the only point where a model touches the briefing. It receives the already-settled item list and returns exactly one string; no schema lets it add, drop, reorder or re-date an item, and a failed, empty or overlong reply drops the paragraph while the full list still renders. Commitment content is withheld from external providers through the same gate as `commitmentContextEnabled`, filtered immediately before model invocation. Briefing state is cached in process memory per profile and local date — never in SQLite — and refresh is an explicit user action.
- Variants and states: every data component covers loading, empty, error, success, disabled and policy-locked states; commitments additionally cover active, blocked, paused, completed, overdue and due-soon; memory additionally covers active, archived, internal-only, external-allowed and expired; ChatGPT account additionally covers Codex CLI unavailable, signed out, browser login pending, signed in, quota unavailable, model catalog loading/empty/error and logout pending.
- Token/component ownership: CSS variables in `apps/desktop/src/renderer/styles.css` own visual tokens; shared domain/IPC types own state vocabulary; renderer components must not invent parallel status strings.

## Accessibility

- Target standard: WCAG 2.2 AA for renderer surfaces.
- Keyboard/focus behavior: all flows complete without a pointer; tabs use arrow/Home/End navigation; dialogs trap and restore focus; destructive and external-sharing choices require an explicit control.
- Contrast/readability: semantic state is never color-only; long content wraps; technical identifiers remain selectable and use monospace only where useful.
- Screen-reader semantics: meaningful headings, labels, live regions for async status and explicit descriptions for scope, sharing and irreversible actions.
- Reduced motion and sensory considerations: honor `prefers-reduced-motion`; avoid flashing, pulsing status and surprise audio.

## Responsive behavior

- Supported breakpoints/devices: Windows desktop first; application window from 520 x 520 through wide desktop, with 1280 x 860 as the default.
- Layout adaptations: below 760 px collapse multi-column surfaces and allow horizontal settings tabs; below 620 px stack navigation and content while keeping primary actions visible.
- Touch/hover differences: hover may reveal secondary actions on desktop, but the same controls must remain keyboard reachable and visible on touch-sized layouts.

## Interaction states

- Loading: show the object being loaded and keep unrelated navigation usable.
- Empty: explain the user outcome and offer one primary next action; avoid generic “start typing” copy when a contextual action is available.
- Error: preserve user input, show a plain-language cause, request/operation identifier when useful and one recovery action.
- Success: confirm the resulting state or object, not merely that a request completed.
- Disabled: explain the prerequisite or policy owner; do not silently disable.
- Offline/slow network: distinguish local availability from provider/MCP availability; memory management and local history remain usable.
- ChatGPT login: opening the system browser is the only handoff. Nexa keeps the pending state visible until Codex App Server reports completion, then displays the returned account and plan. A missing Codex CLI is an actionable local prerequisite, not an authentication failure.
- ChatGPT models: keep the catalog heading visible so signed-out and policy-locked states explain the prerequisite. After login, load models without blocking account details and refresh the Chat picker immediately; a catalog failure preserves the signed-in state and offers refresh/update-CLI recovery. If a conversation references a Codex model that is no longer available, preserve the destination and disable sending instead of silently switching providers.
- Background boundary: check-in scheduling only runs while the Nexa process is alive and opt-in is enabled. Closing the app on Windows/Linux stops it, and no copy may imply otherwise. While the process is alive, a check-in may raise an OS notification, but delivery is never claimed: Do Not Disturb, focus assist and group policy all swallow a toast without reporting an error, so Today remains the only source of truth. Reminders after the app exits are still out of scope — they need a real background process and a decision about the decrypted credential cache.

## Content voice

- Tone: natural Vietnamese, calm, concise and respectful. Lead with the outcome.
- Terminology: use `Nexa nhớ`, `gợi ý`, `hành động`, `chờ bạn xác nhận`, `chỉ dùng nội bộ` and `cho phép gửi ra ngoài tổ chức`; avoid anthropomorphic claims such as feelings or consciousness.
- Microcopy rules: name the destination and consequence before consent; uncertainty is explicit; buttons use concrete verbs; do not imply that archived memory is deleted.

## Implementation constraints

- Framework/styling system: Electron, React and repository-native CSS; no new UI or state dependency without an explicit decision.
- Design-token constraints: extend the existing CSS variables and semantic classes; do not introduce a second token system.
- Performance constraints: preserve the existing startup and memory budgets; local memory retrieval is bounded and must not trigger an additional LLM call.
- Compatibility constraints: renderer remains untrusted, has no direct network/filesystem/secret access, and all inputs cross validated IPC. ChatGPT-managed login requires a locally available Codex CLI with `app-server`; Nexa does not bundle or download a second executable in this slice.
- ChatGPT authentication/runtime constraints: use stable Codex App Server account, `model/list`, thread and turn methods; keep OAuth/token lifecycle inside Codex; validate the returned external sign-in URL in main before opening it; page and bound model results before IPC; never log the URL, email, token, prompt, response or raw App Server payload; reject unsupported server requests; stop the child process during app shutdown.
- Codex context constraints: inject only bounded, non-deleted, completed user/assistant text from the current Nexa conversation. Do not inject tool records, memory facts, attachments or another conversation. Ephemeral Codex threads prevent a second persistent conversation ledger outside Nexa.
- Privacy constraints: memory is encrypted at rest, manually confirmed, bounded in context, scoped to a conversation or globally, and internal-only by default. External-provider sharing is explicit per fact and filtered again immediately before model invocation.
- Activity/check-in constraints: global preference stays in encrypted profile settings; check-in operational rows contain no duplicated sensitive content; all timeline/check-in IPC is bound to the current profile in main. Existing confirmation, payload binding, tool authorization and uncertain-operation recovery remain unchanged.
- OS notification constraints: both notification preferences live in encrypted profile settings and default to off. Notification text and the log lines about it carry a count and a boolean, never a commitment title, next action, internal id or trigger timestamp — application logs are written to disk outside the SQLite encryption boundary and are held to the same content policy as the toast. Platform support is re-read for each Settings load so an unsupported platform disables the switches with a stated reason instead of enabling a feature that cannot run. `app.setAppUserModelId` matches `appId` in `electron-builder.yml` so Windows attributes toasts to Nexa rather than to Electron.
- Bank checklist constraints: templates are read-only versioned resources distributed by IT; checklist logic lives in a pure package separate from BA document schemas; extraction output is schema-validated and retry-bounded; file tokens are consumed and released in main; review and persistence stay bound to the current profile.
- BA local tool constraints: BA tools are prefixed `nexa_ba_`, sit outside the Atlassian presets and are appended to the tool block as a group when `baWorkbench` is on. The set of possible `tools` prefixes therefore stays finite and known in advance (ADR 0009): adding a tool to that fixed set is fine, selecting BA tools per question is not. The first slice is read-only; there is no BA delete tool, and an agent can never set a knowledge item to `confirmed`.
- Local tool constraints: local tools are a closed registry built per turn in main; they resolve before MCP names, never route through `mcp.callTool`, and get no MCP read access when building a preview. Their previews declare a `local` target system so the confirmation dialog states the data stays on the machine. Commitment ownership is re-checked against the current profile in main before every preview and every write.
- Test/screenshot expectations: targeted unit/integration tests, full `pnpm verify`, Electron E2E for critical memory flows, and Playwright screenshots at default and narrow desktop widths for major new surfaces.

- BA data constraints: all BA tables are prefixed `ba_`, cascade on `profile_id` and store every piece of business content encrypted. No plaintext column holds business content — joins, deduplication and aggregation run on decrypted objects in main, the same way encrypted conversation search works. Logs and diagnostics carry ids, enums and counts only.
